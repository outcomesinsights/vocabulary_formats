Ryan, 2026-08-12:

> "I would like vocabulary_formats to be the best example of how to detect/validate codes. I'm not
> sure I understand your concern about detection vs validation. also, if the ^ and $ in the formats
> table is upsetting to downstream consumers, should we place between \b instead or just have no
> start/end indication and just have it assumed that there should be some sort of start/end boundary
> and that the content of the column is something that detects the code in its entirety?"

## FIRST, THE DETECTION-VS-VALIDATION CONCERN WAS OVERSTATED. Correcting it here.

It was framed as though a format and a detector need DIFFERENT PATTERNS. They do not. Two separable
things were conflated:

  BOUNDARY     Where the match starts and ends. A packaging concern, and Ryan's proposal solves it.
  PERMISSIVENESS  How much the shape admits. This is the only real tension, and it is narrower than
                  it looked.

The residual tension is real but small: this repo keeps positions 2-3 of ICD10CM as \\w ON PURPOSE,
so a new shape like FY2026's QA0 needs no edit. Used unanchored in prose, that headroom becomes
false positives. BUT in the one consumer that actually scans prose (icd10cm's note extractor), most
of the strictness comes from CONTEXT, not from the code shape -- parentheticals, and trigger words
like 'codes' / 'category' / 'classifiable to' before a bare code. Context is document-specific and
belongs to the consumer. The SHAPE is the vocabulary's and belongs here.

So the split is not two patterns. It is: ONE shape here + boundary supplied by the consumer +
context grammar supplied by the consumer. Which is exactly what Ryan proposed.

## SECOND, THE ANCHORS ARE ACTIVELY WRONG TODAY -- not merely inconvenient

^ and $ are LINE anchors in Ruby, not string anchors. Verified 2026-08-12 against the shipped
ICD10CM pattern:

    /^\\w{3}(\\.\\w{1,4})?$/ =~ "A00\\nDROP TABLE codes"   ->  MATCHES
    /^\\w{3}(\\.\\w{1,4})?$/ =~ "junk\\nA00"               ->  MATCHES

code_set_catalog is the Ruby consumer. A multi-line string whose ANY line is a code currently
validates as a code. \\A..\\z is the Ruby spelling and this table cannot supply it, because the right
spelling differs per language -- which is precisely the claim this repo makes about itself
('language-neutral source-of-truth'). Shipping ^..$ silently contradicts that.

## THIRD: \\b IS THE WORSE OF THE TWO OPTIONS

  - It still bakes in ONE boundary policy. A validator wants whole-string; a prose scanner may want
    (?<![0-9A-Za-z.]) so that 'X.QA0' does not match; a claims parser may want something else.
  - \\b is defined on \\w, so it behaves oddly around the DOT that half these vocabularies use.
  - Its semantics vary across the engines this table serves (Ruby, Python re, R, DuckDB).

Storing NO boundary is strictly more composable and is the only option that stays language-neutral.

## FEASIBILITY -- checked, and it is clean

All 34 rows were tested for a TOP-LEVEL alternation once ^ and $ are stripped -- the failure mode
where a consumer wrapping the pattern in \\A..\\z would bind the anchor to the first alternative only.
ZERO rows have one: every row with alternation (ICD9CM, ICD10, ICD10.DOTLESS, ICDO3) already carries
an outer group. So stripping is mechanically safe today. It must be a documented INVARIANT going
forward, not luck: every row is a single self-contained group.

One row needs judgment: ICDO3 is ^\\s*(...)\\s*$, where the \\s* accommodates a known upstream defect
(concept 36402927 has a trailing space). Whitespace tolerance is arguably the consumer's job too.

## THE MIGRATION IS THE RISK, NOT THE EDIT

Stripping anchors in place is a SILENT semantic change for any consumer that does an unanchored
match today: validation quietly becomes substring-match, so everything containing a code passes.
That fails toward FALSE POSITIVES, which is the direction this repo tolerates least badly -- but it
is still silent, which is the failure class the trellis exists to stop.

Known consumers: code_set_catalog (Ruby), code_collector (Python, planned -- bead
code_collector-i3lp), carveR (R). NOTE carveR fetches
raw.githubusercontent.com/.../vocabulary_formats.csv, and that file was DELETED in commit 446f5cb
'Switch to tab-delimited file'. Its fetch is already 404 -- so it is not a migration blocker, it is
a separate live break.

## OPTIONS

  A. Strip anchors from the regexp column in place; document the convention; update consumers.
     Cleanest end state. Silent behaviour change for any consumer not updated in lockstep.
  B. Keep regexp as-is and ADD a boundary-free column; consumers migrate at their own pace.
     No silent breakage. Two columns to keep in sync, which is its own rot.
  C. Strip anchors AND rename the column (e.g. regexp -> pattern). A consumer reading the old name
     breaks LOUDLY at the read rather than silently at the match.

C is worth serious weight: it converts a silent semantic change into a visible missing-column error,
which is the same reasoning the note-reference rename used upstream (rename and re-key in ONE
release so a stale query errors instead of returning wrong rows).

## IF THIS IS ADOPTED, THE README SHOULD CARRY THE RECIPES

Per language and per job, so 'best example of how to detect/validate codes' is demonstrated rather
than asserted: whole-string validation (Ruby \\A..\\z, Python re.fullmatch, R ^..$ with perl=TRUE),
and detection in prose ((?<![0-9A-Za-z])..(?![0-9A-Za-z]) plus the caution that context, not shape,
is what keeps a prose scan clean).


## THE BLAST RADIUS, ENUMERATED 2026-08-12 -- it is TWO repos, and one is already dead

Swept every non-archived repo under ~/projects/outins for references, then filtered to actual
SOURCE reads of the regexp column (excluding docs, blog posts, XML code summaries and tracker
files). Mentions are many; readers are two.

### 1. litmine -- LIVE, Python, breaks SILENTLY

    validate.py:103   out[row['vocabulary_id']] = re.compile(row['regexp'])
    validate.py:282   if any(pat.match(s) for pat in regexes for s in candidates)

`re.match` anchors the START ONLY. The end anchor comes entirely from the row's own $. Strip it and
validation becomes a PREFIX match -- demonstrated:

    'I10'                          anchored=True   stripped=True
    'I10 and some trailing prose'  anchored=False  stripped=True
    'I10DROPTABLE'                 anchored=False  stripped=True

FIX IS ONE WORD: re.match -> re.fullmatch. That is also strictly better than the status quo, since
fullmatch does not depend on the data carrying an anchor at all.

### 2. carveR -- ALREADY BROKEN (404), R, would break WORSE

    R/column_code_checks_targets.R:170  vocabulary_formats[vocabulary_id == v, c('regexp')][[1]]
    R/column_code_checks_targets.R:172  regexp <- paste0('(', paste0(regexps, collapse='|'), ')')
    R/column_code_checks_targets.R:85   stringr::str_detect(code, col_info[['format_regexp']])
    R/bad_code_prototype.R:37           the same call, duplicated

`str_detect` is an UNANCHORED substring search. It depends on BOTH ^ and $ from the data, and it
ORs several rows together into one group. Strip the anchors and it becomes 'does this string
CONTAIN something code-shaped' -- so 'garbage I10 garbage' passes. Total silent widening.

It is moot until the fetch is fixed: carveR pulls vocabulary_formats.csv, deleted in 446f5cb
(bead vocabulary_formats-o4c). FIX: wrap at the call site, paste0('^(', ..., ')$').

### NOT AFFECTED, checked rather than assumed

  code_collector     COMMENTS ONLY. It respells the shapes locally (bead code_collector-i3lp will
                     make it a real consumer -- write it anchored at the call site from day one).
  code_set_catalog   Not a reader at all. lib/code_grammar.rb respells the shape (csc-3nb8 weighs
                     adoption). Note it is RUBY, where ^/$ are LINE anchors -- so if it ever adopts
                     the table, it needs \\A..\\z regardless of what this column carries.
  oimnibus           Blog posts and generated XML code summaries. Not code.
  pman, codesistant  References in prose/trackers only; codesistant is still empty.

## WHAT THIS DOES TO THE DECISION

It makes option C (strip anchors AND rename regexp -> pattern) cheaper than it looked. The migration
is two one-line changes in repos we control, one of which is already broken and needs touching
anyway. The rename converts carveR's silent widening into a loud missing-column error at the read.

It also strengthens the case on the merits: BOTH readers today are relying on anchors they did not
write and cannot see, and both are subtly wrong about which end is covered. litmine covers the start
by accident of re.match; carveR covers neither. Data carrying anchors is what let both ship without
noticing.
